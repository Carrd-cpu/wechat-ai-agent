# 企业微信 AI 智能客服助手（模拟版）

一个可以现场演示的 **AI 客服 Agent**：模仿桌面微信的客服工作台，客户发消息后，Agent 会
**识别意图 → 命中 Skill → 调用工具 → 查知识库 / 查订单 / 开工单 → 生成回复**，遇到高风险问题自动转人工。

- 纯 Python 标准库 + 原生 HTML/CSS/JS，**零第三方依赖**，不用联网也能跑
- 有 API Key 时走真实大模型（OpenAI 兼容 function calling），没有则自动降级为离线规则引擎，**演示不会翻车**
- 右侧「Agent 运行轨迹」面板实时展示每一步推理，方便面试官看清它为什么这么答

## 一、怎么启动

双击 `start.bat`，或在当前目录执行：

```bash
python server.py
```

浏览器会自动打开 `http://127.0.0.1:8000`（8000 被占用会自动换 8001–8010）。
停止服务：控制台按 `Ctrl + C`。

## 二、三分钟演示脚本

1. 点右上角 **一键演示**（会自动跑完下面 4 轮，也可以手动输入）：
   - `你好，我们买的客服系统部署到哪一步了？` → 命中 `order-query`，调用 `query_order`，回答订单号、进度、交付时间、负责人
   - `那大概什么时候能上线？` → 没有显式关键词，靠上下文补全为订单追问，切成短答（展示多轮记忆）
   - `费用是多少？后面续费怎么算？` → 命中 `product-consult`，检索知识库，只按知识库口径回答
   - `昨天机器人把价格答错了，客户直接投诉了` → 安全策略命中「投诉」，直接 `transfer_human`
2. 转人工后输入框变成人工客服的嘴替，发一句话，客户侧会看到蓝色「人工客服」气泡
3. 点 **恢复 AI** 交还给智能体；点 **重置** 可以清空重来
4. 想强调「Agent 不是聊天机器人」时，指着右边轨迹面板讲：意图识别 → Skill 路由 → 工具调用 → 工具返回 → 生成

其他可现场演示的点：

| 场景 | 输入 | 观察点 |
| --- | --- | --- |
| 指定订单精确查询 | `我的订单 ZW20261020004 怎么样了` | 正则抽单号 → 工具精确命中 → 已交付话术 |
| 查不存在的订单 | `订单 ZW99999999999 查一下` | 明确说查不到并请核对，**不编造** |
| 知识库兜底能力 | `系统能接公众号和小程序吗？` | 命中「接入渠道」，顺带提到个人微信的合规风险 |
| 跨客户切换 | 左侧点「陈晨 / 新客户咨询」再问价格 | 不同客户、不同上下文，各自独立会话 |

## 三、目录结构

```text
wechat-ai-agent/
├─ start.bat              一键启动
├─ server.py              零依赖 HTTP 服务 + REST API
├─ agent.py               Agent 内核：意图识别 / Skill 路由 / 工具 / 双引擎
├─ config.json            模型、Agent 人设、安全策略
├─ skills/                Skill 定义（每个目录一个 SKILL.md）
│  ├─ order-query/SKILL.md
│  ├─ after-sales/SKILL.md
│  ├─ product-consult/SKILL.md
│  └─ human-handoff/SKILL.md
├─ data/                  客户、订单、知识库、工单、会话（JSON 模拟数据库）
└─ web/                   仿桌面微信前端（index.html / style.css / app.js）
```

## 四、Agent 是怎么搭的

```text
客户消息
  ↓
① 安全策略      命中「投诉 / 律师 / 人工」等关键词 → 直接转人工
  ↓
② 意图识别      规则识别（订单查询 / 售后 / 价格 / 产品 / 打招呼 …）
  ↓
③ Skill 路由    按 SKILL.md 里的 triggers 打分，选中最合适的 Skill
  ↓
④ 工具调用      query_order / search_knowledge / create_ticket / transfer_human
  ↓
⑤ 生成回复      LLM 引擎（function calling）或离线引擎（模板 + 工具结果）
  ↓
⑥ 兜底          查不到 / 没命中 → 不编造，带上下文转人工
```

### Skill 是什么

每个 Skill 就是一份给 Agent 的专业作业说明，放在 `skills/<name>/SKILL.md`，由三段构成：

- **frontmatter**：`name`、`description`、`triggers`（触发词）、`tools`（允许用的工具）
- **执行流程**：先做什么、用什么工具、回复写成什么样
- **约束**：不能承诺什么、什么情况必须转人工

改 Skill 不用改一行 Python：加一个目录、写一份 `SKILL.md`，重启即生效（例如再加一个 `invoice/SKILL.md` 专门处理开票）。

### 工具是 Agent 唯一的事实来源

订单状态、工单号只能来自工具返回值。LLM 模式下用标准 `tools` 参数做 function calling（最多 4 轮），
工具返回结果回灌给模型再生成话术；离线模式则用同一套工具 + 模板生成。两条路径共用同一份工具代码，
保证「有 Key / 没 Key」演示效果一致。

### 接入真实大模型

在项目根目录新建 `.env`（或直接设置环境变量）：

```ini
LLM_API_KEY=你的Key
```

`config.json` 默认指向 DeepSeek，任何 OpenAI 兼容接口都可以，改 `base_url` 和 `model` 即可：

```json
"llm": { "base_url": "https://api.deepseek.com/v1", "model": "deepseek-chat" }
```

启动时控制台会打印当前引擎；页面右上角角标会显示 `LLM 引擎` 或 `离线规则引擎`。

## 五、面试时可以这样讲

**这个项目是什么**
> 我用 AI 编程工具独立做的一个 AI 客服 Agent 演示。前端是仿桌面微信的客服工作台，后端是 Python，
> Agent 负责识别客户意图、命中对应的 Skill、调用工具查订单或知识库，再生成回复；风险问题自动转人工。

**Skill 和 Agent 的关系**
> Skill 是给 Agent 的作业说明书，写在 SKILL.md 里，包含触发条件、执行流程和约束。Agent 是调度者：
> 先判断意图，再选 Skill，Skill 决定调哪些工具，最后组织语言。这样业务流程可以沉淀成文件，
> 改业务不用改代码，也方便做回归测试。

**什么叫训练 Agent**
> 我理解企业里的 Agent 训练大多数不是调模型参数，而是配置角色和 System Prompt、接入知识库、
> 配置 Skills 和工具、设计多轮流程，再用测试用例看回答对不对，持续改 Prompt 和知识库。
> 我这个 Demo 就是按这个思路做的：先定工具和事实来源，再写 Skill，最后用一批问题回归。

**AI 生成代码怎么排查**
> 我会先跑起来看现象，定位是意图识别、Skill 路由、工具参数还是生成环节出的问题——这个项目右侧的
> 轨迹面板就是为此做的，每一步都有记录。定位到环节后再看具体代码和输入输出，改完用同一批用例回归。

**边界与不足**
> 个人微信没有做非官方协议接入，涉及账号风控和平台规则，所以目前是模拟聊天窗口；真实落地会走
> 企业微信或官方客服接口，在客户授权下接入。知识库现在是关键词 + 二元组检索，量大以后会换成向量检索。

## 六、已知限制

- 会话、工单存在本地 JSON 里，重启不会丢，但不是真正的数据库
- 离线引擎是规则模板，语义理解不如大模型；有 Key 时效果明显更好
- 只做单机演示，没有登录、权限和多坐席分配
